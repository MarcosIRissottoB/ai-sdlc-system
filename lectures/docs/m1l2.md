Bases Técnicas para la Integración de un LLM
La Chat Completions API es el punto de inicio para la mayoría de developers cuando integran modelos grandes de lenguaje. Proporciona una forma estructurada de enviar el historial de una conversación y recibir respuestas inteligentes y conscientes del contexto. Esta abstracción elimina la complejidad de gestionar los internals del modelo, permitiéndote enfocarte en construir aplicaciones prácticas.

Desde una perspectiva técnica, un LLM expuesto por API tiene un conjunto pequeño de “building blocks” que llamas desde tu código, más algunas restricciones alrededor de las cuales debes diseñar. Dominar tanto los componentes como sus límites te permite construir features confiables, conscientes del costo y listas para producción.

Al elegir un model, determinas capacidad y costo, pero hay otros parámetros esenciales que también afectan los outputs:

temperature ajusta la creatividad (más bajo para outputs predecibles, más alto para outputs diversos)
max_tokens limita la longitud de la respuesta y el costo
Entender cómo ajustar estos parámetros te ayuda a controlar tanto la calidad como la eficiencia de las respuestas, adaptando el comportamiento de la IA a tu caso de uso.

Una vez entiendes cómo los parámetros del model afectan el comportamiento, el siguiente paso es ver cómo se integra realmente un LLM a través de la API.

A nivel de implementación, varios componentes clave definen cómo tu aplicación se comunica con el modelo:

API Endpoint: el endpoint es la URL HTTPS a la que tu app envía requests (por ejemplo, /v1/chat/completions). Trátalo como cualquier service boundary: usa timeouts, retries con backoff ante 429/5xx e idempotency keys para reintentos seguros. Versiona el endpoint en tu client para poder actualizar sin romper el código existente. En la práctica, lo centralizarás en un pequeño “LLMClient” o módulo de servicio para que todo el equipo use el mismo camino endurecido y con telemetría.
API Key: la API key autentica tus llamadas y debe tratarse como un secreto: nunca hardcodeada, nunca commiteada en Git y nunca impresa en logs. Cárgala desde variables de entorno o un secrets manager (por ejemplo, AWS Secrets Manager, Vault) y pásala mediante el header Authorization. Usa keys separadas por entorno (dev/stage/prod) para controlar el blast radius y rótalas periódicamente. Para servicios compartidos, agrega cuotas livianas de uso y alertas para evitar que un consumidor ruidoso se lleve tu presupuesto.
Payload (JSON): el body de tu request contiene el “qué” y el “cómo”: el prompt/messages más parámetros como model, temperature y max_tokens. Mantén un schema limpio (por ejemplo, {model, messages, temperature, max_tokens, tools}), valídalo antes de enviar y redacta PII de los logs. En producción, estandariza plantillas de prompts e incluye un request_id para trazabilidad. Esto ayuda cuando necesitas reproducir una respuesta, comparar variantes o auditar comportamiento entre despliegues.
Rate Limits: los proveedores limitan el throughput de requests o tokens (por ejemplo, requests/minute o tokens/minute). Espera 429 ocasionales y manéjalos con exponential backoff y jitter, además de una cola del lado del cliente para suavizar picos. Para batch workloads, dosifica jobs o shard entre keys/proyectos cuando esté permitido. Para apps interactivas, considera streaming para mejorar la latencia percibida mientras te mantienes dentro de límites.
Context Window: los modelos aceptan solo cierta cantidad de tokens (input + output). Si sobrecargas la ventana, los prompts se truncan o se rechazan, degradando la calidad. Diseña alrededor de esto con compacción de prompt (resúmenes en lugar de hilos crudos), retrieval-augmented generation (solo fragmentos relevantes) y memoria de ventana deslizante para chats. Sé intencional con max_tokens para que el modelo tenga espacio para responder sin explotar el presupuesto.
Costs: pagas por token tanto de entrada como de salida, así que el diseño del prompt es una decisión económica. Controla el gasto acortando system prompts, usando modelos más pequeños/baratos para tareas simples (por ejemplo, classification), configurando max_tokens y cacheando outputs deterministas (temperature bajo) cuando los inputs se repiten. Agrega telemetría de uso (tokens, latencia, costo por llamada) y guardrails de presupuesto; te permiten detectar regresiones temprano y demostrar ROI cuando las features escalan.

La Chat Completions API es la interfaz fundamental para construir aplicaciones de IA conversacional con los modelos de OpenAI. Introduce un formato estructurado que va más allá de prompts de texto plano al enmarcar interacciones como una secuencia de messages con roles asignados. Este diseño refleja cómo los humanos se comunican en diálogo, lo que lo hace ideal para asistentes, chatbots, sistemas de tutoría o cualquier workflow que requiera razonamiento de ida y vuelta.

Este diseño estructurado también habilita un conjunto de capacidades core que hacen que las conversaciones con IA se sientan más naturales, consistentes y escalables:

Memoria Contextual Anclaje de instrucciones Flexibilidad Integración escalable
Los modelos pre-entrenados pueden retener contexto a través de múltiples messages al incluir el historial previo en cada request. Esta continuidad permite interacciones multi-turn naturales, críticas para chatbots, asistentes virtuales y agentes de soporte. Por ejemplo, el modelo puede recordar que un usuario preguntó por “billing” antes y adaptar las respuestas de seguimiento, creando un flujo conversacional más humano. Un system message te permite definir el comportamiento general del modelo. Este message actúa como una regla persistente como “Always respond in Spanish” o “Adopt a professional tone.” Al anclar instrucciones a nivel system, aseguras outputs consistentes entre múltiples interacciones, reduciendo variabilidad y mejorando control del comportamiento. Los modelos pre-entrenados son altamente adaptables: pueden realizar tareas como summarization, classification, escritura creativa y reasoning con la misma arquitectura. Esta flexibilidad los convierte en una herramienta universal para prototipado rápido: la misma API puede resumir documentos en un proyecto y generar diálogo en otro, simplemente cambiando el prompt. Como estos modelos se entregan vía endpoints HTTPS, pueden integrarse fácilmente en cualquier sistema moderno. SDKs y librerías en Python, JavaScript y otros lenguajes simplifican setup y manejo de errores, permitiendo escalar de prototipo a producción sin re-arquitectura. Esta accesibilidad democratiza la adopción de IA en organizaciones.

Chat Completions Roles
La Chat Completions API organiza cada conversación en torno a tres roles core — system, user y assistant. Estos roles definen cómo el modelo interpreta el input y produce el output, creando una estructura de diálogo predecible y controlable. El role system define el comportamiento general y el tono del modelo; el role user representa el input humano o prompt; y el role assistant contiene la respuesta generada por el modelo. Entender cómo interactúan estos roles es esencial para diseñar conversaciones de IA claras, consistentes y conscientes del contexto.

💻System

Este message define el comportamiento general del modelo. Establece el contexto, el tono y las reglas que deben guiar todas las respuestas.

Por ejemplo, puedes instruir al modelo a “respond in Spanish”, “use a formal tone” o “act as a career coach”. El role system actúa como una configuración persistente que aplica a toda la conversación. Por lo general se instruye sobre el comportamiento, las reglas de interacción, normas, comportamientos a evitar, entre otros.

👤User

Estos son los inputs o prompts que representan los mensajes del usuario en la conversación. Cada user message aporta nueva información, hace una pregunta o solicita una acción. Mueven el diálogo hacia adelante y definen a qué debe responder el modelo.

🤖Assistant

Este es el output del modelo. El role assistant contiene las respuestas generadas por el LLM, que se moldean tanto por el message del user como por las instrucciones iniciales del system. El assistant debe mantenerse alineado con el contexto establecido por el system y responder coherentemente a los inputs del user.

🔧Tool

Este message representa la salida de una herramienta externa (function/tool call) que el modelo solicitó durante la conversación. Cuando el assistant decide usar una herramienta (por ejemplo: buscar información, consultar una base de datos o ejecutar una función), la aplicación ejecuta esa acción y luego devuelve el resultado al modelo usando un message con el role 'tool'. Este rol permite que el modelo incorpore datos reales y actualizados en su respuesta final, manteniendo el flujo conversacional y reduciendo la necesidad de “inventar” información.

🖋️Diseño Basado en Roles
Una vez que la estructura del request está clara, la siguiente capa de ingeniería es entender cómo se representa la conversación. Cada message dentro del array messages tiene un role y un propósito específicos — formando la base de cómo se mantienen el contexto, el tono y el comportamiento entre interacciones.

El array Messagesrepresenta una conversación compuesta por tres roles clave: system, user y assistant. Cada role cumple un propósito de ingeniería distinto. El role system actúa como el “Director”, definiendo reglas y constraints persistentes, como tono, formato de output o políticas de seguridad. El role user es el “Requester”, que aporta la tarea o pregunta que impulsa la respuesta del modelo. El role assistant funciona como el “Responder”, y opcionalmente puede incluir respuestas previas para mantener continuidad, el rol 'tool' en consecuencia es la respuesta de alguna herramienta (funcion) que fue llamada por el modelo apra resolver alguna accion. Este diseño elimina la necesidad de lógica de memoria custom, ya que el historial ordenado de messages se convierte en el estado de la conversación.

🧠Razonamiento detrás del Diseño
Más allá de definir la estructura, es importante entender el razonamiento detrás de esta arquitectura. El diseño basado en roles no se eligió solo por simplicidad: ofrece control predecible y soporta reproducibilidad, esenciales en sistemas de IA listos para producción.

La estructura por roles da a los developers control granular del comportamiento del modelo. El system message impone reglas no negociables, asegurando tono y formato consistentes entre llamadas. Mientras tanto, los messages user y assistant simulan un flujo natural de diálogo, haciendo que las interacciones multi-turn sean fáciles de gestionar. Esta cadena explícita de contexto mejora la reproducibilidad, un factor esencial para debugging, observabilidad y fine-tuning de ingreniería de prompts.

📚Buenas Prácticas
Convertir estos principios de diseño en práctica requiere disciplina. Las siguientes 'best practices' resumen cómo aplicar lógica basada en roles y control de parámetros en entornos reales, manteniendo integraciones estables, eficientes y fáciles de mantener.

Mantén el system message corto, estable y específico del dominio: define esenciales como idioma de salida, estructura (por ejemplo, “responde en JSON”) y reglas de negocio. Para gestionar contexto eficientemente, preserva solo el historial relevante recortando o resumiendo messages antiguos. Esto evita exceder límites de tokens mientras mantiene al modelo coherente. Por último, al pasar inputs largos o complejos, usa delimitadores o nombres de campos explícitos dentro del prompt para que el parsing sea inequívoco y reduzca riesgos de alucinación.

Funcionalidades Avanzadas de Integración
Más allá del manejo básico de messages, Chat Completions incluye un conjunto de capacidades avanzadas de ingeniería diseñadas para despliegue real. La capa avanzada de integración de Chat Completions reúne seis capacidades potentes que hacen que la IA sea lista para producción: Streaming, Structured Outputs, Function and Tool Calling, Tokenization and Context Management, Error Handling with Retries and Rate Limits, y Observability and Telemetry. Streaming entrega interacción en tiempo real, structured outputs aportan control, tool calling agrega reasoning y acción, token management asegura escala, el manejo robusto de errores garantiza confiabilidad, y telemetry aporta insight. En conjunto, convierten la IA conversacional de un prototipo rápido en un sistema diseñado para confianza, performance y longevidad.

SETTING STREAM
True permite que tu aplicación reciba tokens a medida que se generan, habilitando interacción en tiempo real y menor latencia percibida. Es ideal para interfaces de chat, transcripción en vivo o cualquier caso donde el feedback temprano mejora la UX. En el cliente, bufferiza los chunks entrantes y renderiza progresivamente, con posibilidades claras para stop o cancel. Cuando finaliza el streaming, realiza una validación post (por ejemplo, revisar que el JSON esté completo o que la respuesta haya cerrado correctamente) antes de procesar.

STRUCTURED OUTPUTS (Respuestas predecibles)
Structured outputs te permiten restringir respuestas del modelo a formatos machine-readable como JSON, asegurando resultados predecibles y parseables. Al especificar response_format={"type": "json_object"} o al proporcionar un schema, puedes hacer que los outputs cumplan una estructura específica crítica para extracción de datos, automatización de workflows o encadenamiento de APIs. Esto mejora confiabilidad y elimina la necesidad de parseo frágil basado en regex. Para sistemas en producción, valida siempre el payload JSON final y define los límites del schema con precisión para evitar respuestas malformadas o incompletas.

FUNCTION/TOOL CALLING (orquestación determinista)
Function (o tool) calling permite que los modelos disparen lógica determinista dentro de tu aplicación. Tú defines firmas de función y el modelo decide cuándo invocarlas según el contexto. (también hay técnicas y/o parametros que fuerzan el uso de la tool) Por ejemplo, el modelo podría llamar a una función get_user_balance(user_id) cuando le hacen una pregunta financiera. Este enfoque ancla el reasoning del LLM a datos reales, reduciendo dramáticamente alucionaciones y mejorando la confianza. Tu código ejecuta la función y envía los resultados (tool_Response) de vuelta al modelo para síntesis, creando un workflow híbrido donde la IA maneja el “por qué” y tu sistema asegura el “cómo”.

TOKENIZATION & MANEJO DE CONTEXTO
Los LLMs procesan input y output como tokens (sub-word units) que cuentan dentro del límite de la ventana de contexto. Gestionar el contexto eficientemente evita truncamiento y costos inflados. Usa estimadores como tiktoken para medir el tamaño del payload y aplica estrategias como resumir mensajes antiguos, recortar contexto irrelevante y mantener system prompts estables. Para documentos grandes, apóyate en retrieval-augmented generation (RAG) en lugar de embebérselo todo. Cuando el contexto sea incompleto, instruye al modelo a rechazar o pedir aclaración en lugar de improvisar.

ERRORES, REINTENTOS, Y RATE LIMITS
Los sistemas listos para producción deben manejar fallas transitorias con elegancia. Errores de rate limit (429) deberían activar exponential backoff con jitter, mientras que errores del servidor (5xx) requieren retries limitados y circuit breakers. Valida payloads antes de enviar para evitar errores de schema o de tamaño. Refuerza idempotency usando IDs de conversación o de message para evitar acciones duplicadas al reintentar. Por último, gestiona presupuesto de uso de API estimando costos por tokens por request y abortando cuando se excedan umbrales, evitando gastos descontrolados y preservando confiabilidad.

OBSERVABILIDAD Y TELEMETRÍA
La visibilidad es clave para mantener confianza y control en sistemas de IA. Loguea datos estructurados por cada call: versión del prompt, hash del system message, configuración del model, token usage y tipo de outcome (success, parse-fail, tool-call, etc.). Anonimiza o hashea datos del usuario por compliance. Estos logs soportan análisis de costos, A/B testing y detección de regresiones. Correlacionar logs por usuario o sesión ayuda a diagnosticar edge cases y a refinar continuamente la calidad del prompt y el tuning de parámetros.

Con estas capacidades avanzadas, Chat Completions puede aplicarse a una variedad de patrones de integración del mundo real. Cada patrón usa el mismo framework core — roles, structured outputs y tool calling — pero se adapta a diferentes workflows y necesidades del sistema. Desde clasificacion simple hasta pipelines dinámicos de retrieval, estos patrones muestran cómo la misma arquitectura puede impulsar una amplia gama de casos de uso de IA listos para producción:

Single-turn tasks (por ejemplo, clasificacion, extracción) aprovechan salidas estructuradas para respuestas limpias y consistentes.
Multi-turn assistants usan roles e historial de messages para mantener contexto de forma natural.
Tool-augmented agentes combinan razonamiento con llamadas deterministas del sistema para respuestas coherentes.
RAG pipelines recuperan e inyectan contexto dinámicamente desde bases vectoriales para manejar contenido largo o cambiante.

Este patrón validate, retry y enforce structure es una buena práctica para integraciones en producción donde consistencia, seguridad y observabilidad importan.

Comparativa de Proveedores: Claude, Gemini y más allá
Aunque OpenAI domina gran parte de la práctica actual de AI engineering, los sistemas listos para producción nunca deberían depender de un solo proveedor. Claude (Anthropic) y Gemini (Google) ofrecen APIs comparables, con distintos trade-offs en costo, seguridad, profundidad de razonamiento y tamaño de context window. Entender estos proveedores es esencial para resiliencia arquitectónica e independencia de proveedor.

¿Por qué Importa?
Abstracción : al aprender cómo difieren las APIs, los ingenieros diseñan capas de abstracción que permiten cambiar proveedores sin reescribir lógica de negocio.
Optimización : cada proveedor tiene fortalezas: context windows más grandes, respuestas más rápidas o defaults orientados a seguridad.
Manejo de riesgo: evita depender de un proveedor y mitiga cortes de suministro, cambios de políticas o variaciones de precio.
Piensa en cada proveedor de IA como un estándar distinto de enchufe. El dispositivo (tu aplicación) es el mismo, pero necesitas el adaptador correcto (API client, parámetros, estilo de prompt).

Una buena práctica de ingeniería es usar un adaptador universal (una capa de abstracción en código), para conectarte a OpenAI, Claude o Gemini sin “recablear” todo.

⌥Alternativas en el Ecosistema: Claude y Gemini
Proveedores importantes como Claude (Anthropic) y Gemini (Google) ofrecen opciones sólidas según tus necesidades. Entender sus fortalezas y trade-offs ayuda a diseñar integraciones agnósticas y a tomar decisiones informadas.

Claude utiliza una API similar basada en mensajes estructurada en torno a los roles de usuario, asistente y sistema, pero con convenciones de nombres ligeramente diferentes. Sus ventajas clave incluyen ventanas de contexto excepcionalmente grandes (hasta 200k tokens), una fuerte alineación de seguridad y un excelente rendimiento en tareas de razonamiento y resumen, especialmente para documentos extensos.

Sin embargo, Claude puede ser excesivamente cauteloso en ciertas respuestas debido a sus filtros de seguridad, y sus funciones de llamada a herramientas o funciones son menos flexibles que las de OpenAI, lo que lo hace ideal para flujos de trabajo con mucho texto, pero menos para sistemas orquestados e impulsados por herramientas.

Gemini, parte de Google AI Studio, es una plataforma nativa multimodal diseñada para manejar texto, imágenes y código de forma nativa. Sus mayores fortalezas residen en una integración multimodal fluida y una estrecha alineación con los servicios de Google Cloud, ofreciendo un despliegue sencillo para los equipos que ya se encuentran en ese ecosistema. Logra un buen equilibrio entre la calidad del razonamiento y la velocidad de inferencia.

Sin embargo, sus herramientas para desarrolladores aún están madurando y muchas capacidades avanzadas están vinculadas a Google Cloud, lo que puede limitar la portabilidad. Para los equipos que ya utilizan GCP, Gemini ofrece una alternativa potente e integrada; para otros, su ecosistema cerrado puede ser una limitación.

class Provider:

def summarize(self, ticket) -> dict: ...

class OpenAIProvider(Provider):

def summarize(self, ticket):

       return openai_summarize(ticket, response_format="json")

class ClaudeProvider(Provider):

def summarize(self, ticket):

       return claude_summarize(ticket, response_format="json")

class GeminiProvider(Provider):

def summarize(self, ticket):

       return gemini_summarize(ticket, multimodal=True, response_format="json")

class Router:

def init(self, primary="openai"):

       self.adapters = {

           "openai": OpenAIProvider(),

           "claude": ClaudeProvider(),

           "gemini": GeminiProvider(),

       }

       self.primary = primary

def summarize_ticket(self, ticket):

       if ticket.has_image:          # modality-based routing

           return self.adapters["gemini"].summarize(ticket)

       try:

           return self.adapters[self.primary].summarize(ticket)

       except QuotaError:            # 429 or provider-specific quota failure

           return self.adapters["claude"].summarize(ticket)

       except TransientError:        # retry with backoff, then fallback

           retry_with_backoff(self.adapters[self.primary].summarize, ticket)

           return self.adapters["claude"].summarize(ticket)

# Usage

router = Router(primary="openai")

summary = router.summarize_ticket(ticket) # returns {"summary": "...", "confidence": 0.92}

Flujo de Trabajo
🔀De Idea → Prompt → Llamada a la API → Iteración
Un workflow de IA es el proceso disciplinado de transformar una idea de alto nivel en una interacción con un modelo que sea confiable, repetible y testeable. A diferencia de “probar prompts al aire”, un workflow introduce estructura y responsabilidad, asegurando que cada paso —desde la definición del problema hasta la evaluación— pueda reproducirse, medirse y mejorarse. Este enfoque sistemático es lo que convierte experimentos rápidos en funcionalidades de IA listas para producción. Al seguir una secuencia clara de etapas, los ingenieros pueden razonar sobre el comportamiento del modelo, identificar fuentes de error y escalar patrones exitosos entre equipos y productos.

El workflow se despliega en cuatro fases clave. Empieza con la Idea, donde definís el problema con precisión, identificando el objetivo, los resultados esperados y las métricas de evaluación. Luego viene el Diseño del Prompt, donde traducís el problema a un lenguaje estructurado que el modelo pueda entender. Este paso requiere balancear claridad, contexto y restricciones para obtener resultados consistentes. La etapa de Llamada a la API ejecuta ese prompt a través del endpoint del modelo, combinando parámetros (como temperature y max_tokens) que influyen en el determinismo y el rendimiento. Por último, en la Iteración, analizás la salida, refinás el prompt o los parámetros y validás las mejoras, tratando la interacción con el modelo como un bucle de feedback de ingeniería, no como un experimento aislado.

Podés pensar este proceso como compilar y depurar código. La fase de Idea se parece a la especificación de requisitos: definir qué debería hacer tu “programa” (el modelo). El Diseño del Prompt es como escribir el código: expresar la lógica de forma estructurada y legible por una máquina. La Llamada a la API funciona como la compilación/ejecución, donde corrés el sistema y observás la respuesta. Y la Iteración representa el debugging: corregir ambigüedades, ajustar restricciones y testear hasta que el comportamiento se estabilice. Así como ningún ingeniero entrega software después de una sola ejecución, ningún AI Engineer debería confiar en la primera respuesta del modelo.

La iteración no es un defecto: es el mecanismo por el cual emergen la confiabilidad, la consistencia y el rendimiento.

Casos de Uso
📋Clasificación y resumido en escenarios de producción (mejorado)
Un caso de uso en ingeniería de IA es una aplicación concreta y medible de un modelo para generar resultados de negocio. Acá nos enfocamos en dos patrones fundamentales y de alto ROI:

Clasificación (Classification): asignar una o más etiquetas a un input (triage, enrutamiento, spam, intención). Las prioridades son precisión, recall y consistencia.
Resumido (Summarization): condensar texto largo en una salida concisa (briefings, notas de reuniones, logs de soporte). Las prioridades son fidelidad, cobertura y brevedad.
Estos patrones muestran cómo llevar a producción todo lo aprendido hasta ahora: diseño de prompts, parámetros, salidas estructuradas, disciplina de workflow, evaluación, control de riesgos y gestión de costos.

🧭Guía de decisión: ¿cuándo usar cada patrón?
Pregunta Si la respuesta es “Sí” → Patrón probable Porque
¿Necesita una etiqueta o ruta discreta? Clasificación Permite la automatización (colas, SLA, asignación de propietario)
¿Necesitas una narrativa concisa para los humanos? Resumen Reduce el tiempo de lectura; acelera la toma de decisiones
¿El texto es largo (correos electrónicos, artículos, registros)? Resumen (con objetivos de compresión) Enfoque en la cobertura + fidelidad
¿Los resultados están vinculados a flujos de trabajo (webhooks, colas)? Clasificacion (JSON outputs) Decisiones consumibles por máquina
Tip: Muchos sistemas combinan ambos (por ejemplo, resumir y luego clasificar el resumen; o clasificar primero para elegir un resumidor específico según el dominio).

🗂️Caso de estudio 1 – Clasificación de tickets de soporte (triage y prioridad)
Una empresa B2B SaaS recibe ~500 tickets por día a través de email, chat y formularios web. Cinco agentes L1 leen y enrutan tickets manualmente; el tiempo promedio de primer contacto es de 4 horas, incumpliendo el SLA premium de 2 horas.

📊 Planteamiento del problema
El triage manual es lento e inconsistente. Problemas urgentes (pagos, acceso a la cuenta, caídas del servicio) a veces se enrutan mal, lo que retrasa la resolución y afecta negativamente el NPS.

🎯 Objetivo, KPI y guardrails
Objetivo: clasificar automáticamente los nuevos tickets en {Urgente, Normal, Bajo} y opcionalmente asignar una categoría {Pago, Acceso, Rendimiento, Funcionalidad, Otro}.
KPI principal: reducir el tiempo de primer contacto en ≥75% (por ejemplo, de 4h → ≤1h).
KPI de calidad: precisión ≥95% en un set de validación etiquetado; recall de “Urgente” ≥98% (priorizando capturar todos los urgentes).
Guardrails operativos: umbral de confianza con human-in-the-loop para casos limítrofes.

Diseño de datos y etiquetas
Diseñe etiquetas teniendo en cuenta las acciones posteriores:

Campo Valor Proposito
prioridad Urgente, normal, bajo SLA/velocidad de ruteo
categoria Pago, Acceso, Rendimiento, Características, Otros Selección de equipo/cola
confianza 0.0–1.0 (estimado) Revisar el umbral
razón fundamental corta explicación Auditabilidad y depuración
Inyección de metadatos (opcional): agregue customer_tier, canal, idioma, account_id para mejorar las reglas de enrutamiento y el análisis posterior.

Estrategia de prompting (v1 → v3)
v1 – Clasificador mínimo en JSON
system: Sos un clasificador de tickets de soporte. Respondé SOLO en JSON con las claves: priority, category.
user: Ticket: {{ticket_text}}

v2 – Determinista, con reglas y justificación
system: Clasificás tickets de soporte. Devolvé SOLO JSON con las claves:

priority (Urgent | Normal | Low)
category (Payment | Access | Performance | Feature | Other)
priority (0–1)
category (<= 12 palabras)
Reglas: mención de pago, facturación, login, cuenta bloqueada o caída del servicio → confidence.
Si no estás seguro, seteá rationale.
user: Ticket: priority="Urgent"

v3 – Esquema + captura de evidencia (opcional)
system: Devolvé SOLO JSON con las claves: confidence<=0.6, {{ticket_text}}, priority, category, confidence.
rationale debe citar hasta 20 palabras originales que justifiquen la decisión.
No inventes hechos; si falta información, seteá evidence y evidence.

import os, json

from openai import OpenAI

client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

def classify_ticket(text: str):

messages = [

       {"role": "system", "content": (

           "You classify support tickets. Respond ONLY in JSON with keys: "

           "priority (Urgent|Normal|Low), category (Payment|Access|Performance|Feature|Other), "

           "confidence (0-1), rationale (<=12 words). Rules: Mention of payment, billing, login, account lock, or outage → priority=Urgent. "

           "If unsure, set confidence<=0.6."

       )},

       {"role": "user", "content": f"Ticket: {text}"}

]

resp = client.chat.completions.create(

       model="gpt-4o-mini",

       messages=messages,

       temperature=0.1,

       response_format={"type": "json_object"},

       max_tokens=120

)

return json.loads(resp.choices[0].message.content)

🧩Post-procesamiento
Si confidence<=0.5 y el texto contiene alguno de {critical, P0, outage, error 500, payment} → marcar para revisión.
Si rationale="insufficient details" → enviar a la cola de “triage manual”.
🔍 Protocolo de evaluación
Set de validación etiquetado: armá un set etiquetado (≥200 tickets) con clases estratificadas.
Accuracy: medí accuracy, recall/precision por clase, y especialmente recall(Urgent).
Matriz de confusión: generá una matriz de confusión y analizá los 20 errores principales para refinar prompts.
Latencia, uso de tokens y costo: logueá latencia (p95), uso de tokens y costo ($) por 1k tokens.
Umbral de éxito (ejemplo): accuracy ≥95%, recall(Urgent) ≥98%, p95 latency ≤1.5 s, costo ≤$0.002/request (depende del modelo).

Riesgos y mitigaciones
Falsos negativos en “Urgente”: usar reglas + un umbral de confianza más bajo → revisión humana.
Sesgo / enrutamiento injusto: auditar periódicamente por tier de cliente, idioma y región.
Prompt injection / fuga de PII: eliminar credenciales de los logs; sanitizar inputs; evitar repetir secretos en las respuestas.
Drift: revalidar mensualmente; mantener un pequeño golden set para regresión.

🗂️Caso de estudio 2
Resúmenes ejecutivos de artículos (con evidencia)
Un equipo de investigación revisa ~50 artículos/reportes cada mañana. Leer y resumir toma 15–20 minutos por artículo, lo que limita el volumen y retrasa el brief matutino que se envía a los clientes.

📊 Planteamiento del problema
El resumido manual es un cuello de botella de throughput. Los analistas gastan tiempo en una primera lectura/entendimiento en lugar de enfocarse en síntesis e insights.

🎯 Objetivo, KPI y guardrails
Objetivo: generar 3 bullets respaldados por evidencia por artículo, pensados para ejecutivos.
KPI principal: aumentar artículos por analista por día en +200% (throughput).
KPI de calidad: fidelidad ≥95% (sin afirmaciones sin soporte). Medir cobertura de evidencia (% de bullets con una cita de respaldo).
Guardrails: incluir al menos un fragmento literal por bullet.

Estrategia de prompting (orientada al dominio + consciente de evidencia)
Prompt base
system: Sos un analista financiero. Resumí el artículo en EXACTAMENTE 3 bullets. Cada bullet debe incluir 1 fragmento citado (<= 20 palabras) del artículo que lo respalde. Enfocate en datos cuantitativos, actores clave e impacto de mercado. Devolvé SOLO JSON:
prompts/classifier_v1.txt

user: Article: v2.txt

Compresión y control de estilo (opcional)
Podés agregar restricciones como:
“<= 30 palabras por bullet; evitá adjetivos; preferí números y entidades”.

import os, json

from openai import OpenAI

client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

def summarize_article(text: str):

messages = [

       {"role": "system", "content": (

           "You are a financial analyst. Summarize the article in EXACTLY 3 bullets. "

           "Each bullet must include 1 quoted snippet (<=20 words) from the article that supports it. "

           "Focus on quantitative data, key players, and market impact. Output ONLY JSON with key 'bullets' as an array of {summary, evidence}."

       )},

       {"role": "user", "content": f"Article: {text}"}

]

resp = client.chat.completions.create(

       model="gpt-4o-mini",

       messages=messages,

       temperature=0.3,

       response_format={"type": "json_object"},

       max_tokens=300

)

data = json.loads(resp.choices[0].message.content)

assert len(data.get("bullets", [])) == 3, "Expected exactly 3 bullets"

return data
🔍Protocolo de evaluación
Armá un set de evaluación “held-out” de 20–50 artículos. Para cada bullet, verificá:
Fidelidad (Faithfulness): el contenido del bullet aparece en la fuente (sin alucinaciones).
Cobertura (Coverage): se preservan los hechos clave (números, nombres, fechas).
Brevedad (Brevity): ≤ al límite objetivo.
Trackeá la cobertura de evidencia: % de bullets con una cita válida de soporte.
Medí el ratio de compresión (tokens originales vs tokens del resumen) y el tiempo ahorrado.

🔁 ¡Recapitulación de todo lo aprendido!
Al cerrar esta lección, el foco pasa de la teoría a la aplicación. Aprendiste no solo cómo funcionan los modelos preentrenados, sino también cómo integrarlos, controlarlos e iterarlos de forma efectiva dentro de sistemas reales. Los siguientes puntos resumen los aprendizajes más accionables: principios que podés aplicar de inmediato para acelerar tu práctica como AI Engineer y construir soluciones listas para producción con confianza.

⚡ Usá modelos preentrenados para MVPs. Cuando desarrollás un MVP o una prueba de concepto, aprovechá modelos preentrenados como GPT-4 a través de sus APIs en lugar de entrenar desde cero. Este enfoque te permite integrar capacidades avanzadas de IA en días en vez de meses, habilitando la validación rápida de ideas sin una inversión inicial grande. Al enfocarte primero en la integración, reducís el riesgo, acortás el ciclo de desarrollo y creás prototipos tangibles que luego pueden evolucionar a soluciones personalizadas si el caso de negocio lo justifica.

🎛️ Dominá los parámetros clave. Entender cómo parámetros como temperature y max_tokens moldean el comportamiento del modelo es esencial para tener control y eficiencia de costos. temperature equilibra creatividad y predictibilidad: valores bajos producen resultados consistentes y repetibles, mientras que valores más altos permiten exploración y variedad. max_tokens define el largo de la respuesta, afectando directamente la latencia y el costo. Aprender a ajustar estos parámetros con intención es lo que separa una prueba experimental de un sistema de IA listo para producción.

🔁 Iterá tus prompts de forma sistemática. El prompt engineering es una habilidad iterativa, no una configuración que se hace una sola vez. El primer prompt rara vez sale perfecto. Lo ideal es establecer un ciclo repetible de testeo, medición y refinamiento, registrando cambios y resultados en cada iteración. Tratá los prompts como código versionado: documentá tu razonamiento, evaluá el comportamiento del modelo contra KPIs y optimizá continuamente la claridad y la estructura. Este enfoque disciplinado convierte la experimentación en un proceso de ingeniería predecible.

🧩 Abstraé tu proveedor de IA. Diseñá tu arquitectura para que modelos de distintos proveedores —OpenAI, Anthropic, Gemini u otros— puedan intercambiarse con el menor esfuerzo posible. Esta capa de abstracción evita el vendor lock-in y te da flexibilidad para elegir el mejor modelo para cada tarea según rendimiento, costo o requisitos de compliance. En la práctica, significa envolver los SDKs detrás de una interfaz común y aislar la lógica específica de cada modelo. Este principio simple garantiza adaptabilidad y resiliencia a medida que evoluciona el ecosistema de IA. En conjunto, estos puntos reflejan la mentalidad de un AI Engineer profesional: moverte rápido con inteligencia preentrenada, controlar resultados con parámetros, iterar como desarrollador y diseñar con flexibilidad. Al seguir estos principios, transformás la integración de IA de un experimento aislado a una disciplina de ingeniería sostenible y escalable.
