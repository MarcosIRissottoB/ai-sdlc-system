Introducción
Antes de trabajar con prompts, necesitamos un framework de evaluación. En el desarrollo profesional de IA, el objetivo es simple: dejar de adivinar y empezar a medir.

Cuando integramos un prompt en un sistema —ya sea un bot de soporte o una herramienta de Q&A— la pregunta no es solo si respondió, sino: "¿Valió la respuesta el costo y el tiempo invertidos? ¿Podría un diseño distinto haberlo hecho mejor?".

El Prompt Engineering aporta valor real cuando abandonamos el ensayo y error para entender qué impacta realmente en la calidad, el uso de tokens y la latencia. Ajustar prompts a ciegas es como operar un sistema en producción sin observability: haces un deploy, algo falla y no tienes logs ni métricas que expliquen el porqué.

Al aplicar observabilidad a tus prompts, obtienes visibilidad total sobre:

Consumo de tokens: Impacto directo en costos.
Latencia (Response time): Experiencia de usuario final.
Calidad de salida: Precisión y adherencia a las instrucciones.
Esto transforma el proceso de un arte subjetivo a una disciplina científica. Aprendes cuándo un zero-shot prompt es suficiente y cuándo un patrón de chain-of-thought justifica los tokens extra. El resultado son prompts listos para producción, escalables y, sobre todo, respaldados por datos.

Estrategias de prompting: zero-shot, few-shot y chain-of-thought
En los últimos años, los large language models (LLMs) han transformado la manera en que abordamos el procesamiento de lenguaje natural. Para ingenieros que ya trabajan con APIs y sistemas basados en lenguaje, aprender a promptear estos modelos de forma efectiva es clave para desbloquear todo su potencial.

En esta sección vamos a explorar tres estrategias centrales de prompting, que forman la base de la interacción moderna con sistemas de IA:

0️⃣Zero-shot prompting: pedirle al modelo que realice una tarea sin darle ejemplos.

🔢Few-shot prompting: guiar la salida del modelo incluyendo unos pocos ejemplos bien elegidos.

🧠Chain-of-thought prompting: indicarle al modelo que razone paso a paso para mejorar la precisión lógica.

Aprenderás qué es cada estrategia, cómo funciona y cuándo conviene usarla. Con ejemplos reales de summarization, generación de código y Q&A en dominios específicos, compararemos sus fortalezas, limitaciones y trade-offs. Al final, tendrás un marco práctico para elegir el método de prompting adecuado para tu caso de uso.

0️⃣Zero-shot prompting
Empecemos con el enfoque más simple: zero-shot prompting. Esta técnica le pide al modelo que haga una tarea sin mostrarle ejemplos o demostraciones previas. En lugar de eso, se apoya por completo en el conocimiento pre-entrenado del modelo y en su capacidad para interpretar tu instrucción.

Por ejemplo, si tu objetivo es resumir un artículo corto, podrías escribir simplemente:

“Resume el siguiente artículo en dos oraciones.”
Este método es directo y eficiente. Como no agregas ejemplos al input, mantienes el prompt corto y reduces el uso de tokens, lo que lo hace ideal para escribir un primer prompt y probar rápido el modelo. El zero-shot prompting funciona mejor cuando quieres experimentos rápidos y livianos, o cuando la tarea es lo suficientemente simple como para que el modelo la entienda solo con la instrucción. A menudo es el primer paso del proceso de iteración: perfecto para tener una idea rápida de cómo el modelo maneja tu problema antes de invertir tiempo en diseños de prompt más complejos.

La principal ventaja de este enfoque es la velocidad: se arma rápido, requiere poco o nada de prompt engineering y funciona bien cuando la tarea encaja naturalmente con la forma en que el modelo fue entrenado para seguir instrucciones. Por eso es una gran opción para prototipar ideas o validar una tarea antes de agregar complejidad. Sin embargo, el zero-shot prompting también tiene limitaciones claras: puede producir outputs genéricos o inconsistentes, con menos control sobre el tono, la estructura o el estilo. Para tareas más complejas o especializadas, puede costarle generar resultados precisos, y suele mejorar cuando agregas ejemplos claros o razonamiento paso a paso.

Por ejemplo, si le das al modelo este snippet corto:

A medida que experimentes, probablemente notarás que los prompts zero-shot, aunque son rápidos de probar, a veces pueden dar resultados vagos o inconsistentes. Cuando eso pasa, un siguiente paso útil es agregar unos pocos ejemplos directamente en el prompt: una técnica conocida como few-shot prompting.

🔢Few-shot prompting
En este enfoque incluyes un conjunto pequeño de pares input–output (normalmente dos o tres) antes del input objetivo. Estos ejemplos funcionan como una mini guía: le muestran al modelo qué tipo de respuesta esperas, cómo debe formatearla y qué nivel de detalle debe incluir. En comparación con zero-shot, el few-shot prompting le da al modelo un contexto más claro, lo que muchas veces produce outputs más consistentes y mejor estructurados.

Para que los ejemplos sean efectivos, deben representar inputs típicos y los outputs deseados, estar escritos con claridad y sin ambigüedades. También ayuda incluir pequeñas variaciones entre ejemplos, para que el modelo generalice sin perder consistencia. Cada ejemplo debe emparejar claramente un input con su output correspondiente, formando un patrón simple pero informativo que el modelo pueda seguir.

Por supuesto, esta guía adicional trae trade-offs. Incluir ejemplos hace que el prompt sea más largo, lo que consume más tokens. A cambio, normalmente ganas más control sobre el estilo y la estructura de la respuesta. El riesgo principal es que el modelo imite demasiado tus ejemplos y genere respuestas repetitivas o demasiado “limitadas”.

Para verlo en práctica, imagina que quieres que el modelo genere resúmenes con una estructura y un tono consistentes. En vez de darle una sola instrucción, puedes incluir ejemplos que muestren cómo debería verse el input y el output.

Frente al zero-shot prompting, este enfoque tiende a dar resultados más consistentes y precisos, especialmente cuando necesitas respuestas con una estructura uniforme a lo largo de muchos inputs.

🧠Chain-of-thought prompting
Cuando sales de tareas simples de resumen o de formato, hay problemas que requieren razonamiento más profundo: por ejemplo, corregir un bug que afecta varias partes del código, seguir cómo viajan los datos por un sistema o revisar logs para entender por qué falló algo. En estos casos, puedes usar chain-of-thought prompting: le pides al modelo que siga un proceso paso a paso, manteniendo el razonamiento ordenado para llegar a una respuesta clara y útil.

Este enfoque es especialmente valioso cuando la tarea requiere pensamiento lógico o análisis secuencial: por ejemplo, investigar por qué una app está lenta, rastrear una race condition o entender por qué un deployment falló después de varios cambios. Al darle pasos claros que seguir, normalmente obtienes respuestas más precisas, menos errores y una explicación más entendible de cómo llegó al resultado.

También hay trade-offs. El chain-of-thought suele producir outputs más largos, lo que significa más tokens y mayor latencia. Además, aporta poco valor en tareas triviales o puramente generativas, donde una respuesta corta y directa es suficiente. En resumen: úsalo cuando te importa la calidad del razonamiento y quieres poder revisar (o entender) que cada paso tenga sentido, no cuando solo necesitas una respuesta rápida.

Por ejemplo, imagina que quieres que el modelo resuma un artículo asegurándose de mantener los hechos clave correctos y fáciles de entender. Puedes organizar la tarea en pasos antes de pedir el resumen final:

Al organizar el razonamiento en pasos, el modelo se enfoca primero en los hechos importantes y luego produce un resumen más claro y preciso.

💡Comprender el uso de tokens, la latencia y el costo en la ingeniería rápida

Cuando trabajas con language models modernos, es clave entender cómo medir y controlar el uso de recursos. Esto te ayuda a experimentar de forma eficiente y a manejar costos de producción.

Antes de mandar cualquier request a un modelo, conviene entender qué son los tokens y cómo se cuentan durante una interacción. En cada API call se rastrean tres valores principales: input tokens, output tokens y total tokens.

Tokens: son unidades pequeñas de texto que el modelo usa internamente en lugar de caracteres crudos o palabras completas. Dependiendo del tokenizer, una sola palabra puede dividirse en varios tokens. Por ejemplo, “running” puede convertirse en dos tokens: “run” y “ning”. Cada modelo tiene un máximo de tokens por request. Monitorear tokens te ayuda a evitar errores de truncation y a estimar cost, porque el cobro suele ser por token procesado.
Input tokens: incluyen todo lo que le envías al modelo: prompt, instrucciones, ejemplos o contexto. Determinan cuánta información tiene el modelo para trabajar y afectan directamente el cost. Si tu input excede el límite del modelo, los tokens extra pueden ser truncados o la request puede ser rechazada. Además, el número de input tokens determina cuánto contexto puede usar el modelo; exceder límites puede causar respuestas incompletas o fallidas, y cada input token cuenta para billing.
Output tokens: son los tokens generados por el modelo al producir la respuesta. Mientras más detallado o largo sea el output, más tokens se usan y más sube el cost. Controlar el largo del output con parámetros como max_tokens ayuda a manejar tanto el cost como la latency.
Total tokens: es la suma de input tokens + output tokens en una sola API call. Este valor normalmente lo reporta la API y te da el uso total por interacción.

Ver estos números te ayuda a presupuestar y ajustar prompts: mantener logs solo con lo esencial, poner límites al largo de respuesta cuando solo necesitas un resumen, y reservar few-shot examples para cuando la guía extra realmente mejora la correctness.

📝Medición de la latencia y registro de los parámetros del modelo
Entender cuánto tarda tu modelo en responder y cuánto cuesta cada llamada es esencial para construir aplicaciones eficientes y escalables. Medir latency (response time) y rastrear métricas de uso como tokens y model version te ayuda a tomar decisiones basadas en datos sobre performance y costo.

Cuando hablamos de latency, nos referimos al tiempo entre enviar un request al API y recibir la respuesta del modelo. Esta métrica impacta directamente la experiencia de usuario, el throughput del sistema y la escalabilidad. Medir latency también ayuda a identificar si los delays vienen de tu red, tu aplicación o el modelo en sí. Combinada con token usage, la latency te da una visión completa de cómo el tamaño del prompt, la elección del modelo y el largo del output afectan el performance.

Una forma sencilla de medir latency en Python es registrar timestamps antes y después de tu API call:

TS
PY
Explain
Copy
import time

start = time.perf_counter()

response = model_api_call(prompt)

end = time.perf_counter()

latency_ms = (end - start) \* 1000

print(f"Latency: {latency_ms:.2f} ms")
Luego puedes hacer logging de este valor de latency junto con token counts, model name y otra metadata en un archivo JSON o CSV para analizarlo después.

También es buena práctica registrar qué model version estás usando (por ejemplo, gpt-5 o gemini-2.5-pro). Cada modelo tiene características distintas de performance y pricing, así que guardar este dato hace más fácil comparar eficiencia con el tiempo y proyectar costos con precisión.

🔄Conversión de tokens a costo
Entender cómo el uso de tokens se traduce en costo es esencial para manejar tu presupuesto de API. Cada request a un language model consume input tokens (del prompt) y output tokens (de la respuesta). Los providers cobran según la cantidad de tokens procesados, normalmente con precio por 1M tokens.

Por ejemplo, Gemini 2.5 Pro cobra aproximádamente:

USD 1.25 por 1M input tokens y USD 10.00 por 1M output tokens para requests de hasta 200,000 tokens,
USD 2.50 por 1M input tokens y USD 15.00 por 1M output tokens para contextos más grandes.

USD 1.25 por 1M input tokens,
USD 10.00 por 1M output tokens, y
USD 0.125 por 1M cached input tokens cuando reutilizas el mismo contexto.

Muchas veces, acortar los ejemplos de few-shot, reutilizar cached contexts o simplificar pasos de razonamiento puede reducir el uso de tokens en 20–30%, bajando costos sin sacrificar calidad.
